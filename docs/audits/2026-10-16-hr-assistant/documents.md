# Audit: "New Executive Assistant JD and internal posting, ask before editing and saving"

**Verdict: the command center can't do this today.** It has no action for drafting, editing or saving documents. Its chat model can't read or write files. It does have a working preview, Confirm and save mechanism that a new feature could use.

## 1) What exists today (evidence)
- **Server test** (scratch copy, fake model bridge, `127.0.0.1`): `GET /api/actions` returned 28 actions. None of them deal with documents, job descriptions, postings or templates. All 28 are about applicants, counties, mail, the brain dump, knowledge gaps, candidates, projects or items.
- **Sending the request to `/api/chat`:** it doesn't match the openings parser (`server.py:177`), so it is passed unchanged to the model bridge. The model then runs with `--tools ""` and only the `mcp__agent-os__*` tools (`model_bridge.py:12,58`). It has no file read or write tool, and there is no MCP tool for documents or templates. The best it can do is put text in a chat reply.
- **`/api/act` with a new `item_id`:** returns 404 `unknown item` (`server.py:75-81`). Actions only run against items a provider already shows. The MCP `executive_window.run` tool has the same limit (`mcp_server.py:976-987`).
- **Workaround:** `/api/brain-dump` captured "Draft Executive Assistant job description…" as item `brain-dump:bd-…`. Its only options are `openings.event`, `item.dismiss`, `item.snooze` and `brain_dump.stage_candidate`. It is tracked, but nothing can act on it.
- **Confirm flow works.** I tested it with a prototype `document.save` action in a scratch registry:
  - `Registry.invoke` returns `needs_confirmation`, a single-use token and a diff preview, and nothing is written.
  - `/api/confirm` writes the file.
  - Using the same token again is blocked.
  - The action is recorded in `audit.jsonl`.
  - The window renders `preview.content` as plain text (`gui/executive.js:701`), so a unified diff would display cleanly.
- **A built-in way to ask the user questions exists:** knowledge-gap items plus `knowledge_gap.answer` (`actions_knowledge_gaps.py:63,111`).
- **Existing material to start from:**
  - rtec-hr `sources/job-descriptions/misc-job-descriptions.md` lists the closest roles: Executive Secretary (two sources), Administrative Support Technician and Administrative Assistant/AP. The text of all 12 entries is omitted in git ("Shared searchable text omitted…"). Only hashes and metadata remain.
  - The usable RTEC format ("Position Description / Class Title / Characteristics of the Class / Example of Duties") is in `sources/job-openings-descriptions-2026-09-24/fulltext.part001.md` (CSR) and the receptionist and dispatcher entries.
  - The AAP job-group analysis puts Executive Secretary and Administrative Assistant in "Office & Clerical".
  - **No internal posting template exists anywhere.** `job-applicant-dashboard/Templates` only has the application, the interview checklist, denial letters and email `.txt` files. `openings.py:73` only knows Garage Attendant, Dispatcher and CSR. `template_editor.py` edits email templates only.
- python-docx is installed.

## 3) Design: a "document task" capability
**New modules** (in `src/agent_os/executive/window/`):
- `doc_store.py`: a `DocumentTaskStore` modelled on `brain_dump_store.py` and `gap_store.py`. It keeps task records (`id`, `doc_type` = `job_description` / `internal_posting`, `role`, `seed_sources`, `questions`, `answers`, `draft_revisions`) under `window_home()/documents/`.
- `providers_documents.py`: a provider for open tasks with kind `document_task`. Questions waiting for an answer appear with kind `document_question`.
- `actions_documents.py`: the actions listed below.
- A document helper, `executive/documents.py`: seed lookup, rendering to `.md` and `.docx` (python-docx), and `difflib` diffs.

**Actions:**
1. `document.start` (non-consequential). Called via a synthetic item, the same way `brain-dump-capture` works (`mcp_server.py:939`). It also needs `/api/documents/start` and an MCP `executive_documents.start`. It creates the task, looks up seed job descriptions by role family, and drafts a skeleton in the RTEC "Position Description" format. It returns `questions`: reports to, FLSA status, pay grade, hours, duties to add or remove, qualifications, posting window and how internal staff apply.
2. `document.answer` (non-consequential). Records the user's answers or requested changes on the task.
3. `document.propose` (consequential). Takes a complete `text` param (written by the model or a template) and returns a preview `{title, content: unified diff, questions_open}`. Answers to the questions only change the draft, never the saved file.
4. `document.save` (consequential). On Confirm, writes the exact `params.text` it previewed, plus `.docx`. This follows the outbox/Confirm rule that only the user's click executes.
5. `document.discard`

**Data flow:**
1. Start: draft plus questions.
2. The user answers or edits in chat (`document.answer`).
3. Propose: a diff preview with a token.
4. Confirm.
5. Save, audit, `record_status(completed)`.

Each preview gets its own token, which avoids the 900-second expiry. Audit only `{doc_id, sha256, path}`, not the text.

**Where files are saved:** `.agent-local/executive/documents/<role-slug>/<doc_type>-vN.{md,docx}`. This path is gitignored and must be checked with `local_paths.is_gitignored_local_path`, the way `telemetry.py:605` does. For RTEC, the export path resolves through rtec-hr `rtec_local.private_root()` (`RTEC_HR_PRIVATE_DIR`). Never write to rtec-hr `knowledge/` or to Drive. Promoting a finished job description into the library is a separate ingester step done by a person.
