# Orchestrator OS self-audit: Stage 1 checkpoint

## Scope and method

This is a synthesis of the supplied read-only evidence, not a new run or a code change. The audit snapshot is 2026-09-30. The [context anatomy](self-audit/context-anatomy.md) used `python -m agent_os orchestrate list` and `context-anatomy` (default `--harness-tokens 6000`) on `run-20260930T181109Z-d9a9d8`, `run-20260923T202405Z-5e4d75`, `run-20260924T143653Z-746b90`, `run-20260924T133405Z-dc8cf4`, `run-20260923T200037Z-a1e3c0`, and `run-20260922T200659Z-5b8a73`. These are two complete and four paused runs; the current run was excluded. Prompt tokens there are character-based estimates, not provider usage.

The [usage report](self-audit/usage.md) ran `python -m agent_os orchestrate usage-report` both without a date filter and with `--since 2026-09-16T00:00:00Z`; both covered the same seven runs and 95 calls, with 85 exact-token calls and 10 without token reports. [Foreman](self-audit/foreman.md) ran `python -m agent_os orchestrate foreman strategy`. The [capability audit](self-audit/capability.md) read the 26 `CAP-*.json` records in `projects/personal-agent-os/orchestrator-os/records/capability/`. The [run-event audit](self-audit/run-events.md) read events from the six eligible runs above and excluded `run-20260930T215623Z-77a6c6`. The [test audit](self-audit/tests.md) ran `python -m unittest discover -s tests` and recorded individual module timings. The source files contain the commands, definitions, and per-run detail.

## Candidate fixes for Stage 3

These correspond to the first five ranked problems. In each experiment, measure the incumbent on the same bounded task cohort, then compare the candidate on validation results and **total cost per validated task**. The IMP-0018 promotion rule is strict: promote only when validation is noninferior **and** total cost per validated task falls. Do not use a narrower prompt-token reduction or fewer reviews alone as proof. Keep budget, approval, publication-guard, and privacy gates intact.

## Known evidence gaps

- Usage totals include cache reads and writes within provider input accounting; adding them to input would double count. The report has 10 calls without token reports and supplies no accepted-task denominator ([usage](self-audit/usage.md)).
- The prompt audit estimates tokens from characters and uses a default harness allowance. It measures prompt construction, not actual billed tokens or active time ([context anatomy](self-audit/context-anatomy.md)).
- Events cover six eligible runs and count repeated failures as events. Wall spans include pauses, and attempt medians include planners, reviewers, and repairers; neither is an isolated retry cost ([events](self-audit/run-events.md)).
- Review call usage cannot be joined here to task size, targeted-test results, findings, or validated outcomes. The proposed small-task review saving is therefore unmeasured ([usage](self-audit/usage.md); [events](self-audit/run-events.md)).
- The full-suite failure list is one local Windows worker snapshot; probable-cause labels are estimates, not confirmed root causes ([tests](self-audit/tests.md)).
- CAP success ratios have small samples, `qualified_at_floor` is null in all 26 records, and foreman has no measured-plan ranking ([capability](self-audit/capability.md); [foreman](self-audit/foreman.md)).

## Checkpoint and exact next prompt

Stage 1 established a measured prompt-context opportunity, substantial reviewer-role token use without an eligible-task breakdown, recurring retries and escalations, a failing local full-suite baseline, and weak empirical support for CAP/foreman recommendations. It did **not** establish safe savings from changing review policy or readiness for other repositories. No code or gate changed in this stage.

> **Stage 2 prompt:** Define an explicit Orchestrator OS readiness checklist for developing other repositories. Cover worktree isolation and rollback; secret and privacy boundaries, including the repo map and data directories; validator detection for non-Python repositories; behavior when a repository has no Agent OS project registration; cost and usage caps; review gates; and dirty or large repositories. Create two small throwaway fixture repositories outside any real repository, one Python and one JavaScript. Test each checklist item against both fixtures where applicable, record the exact commands, observed results, and failures, and stop with a checkpoint, evidence, and the exact Stage 3 prompt. Use only subscription and local models, preserve the budget, approval, publication-guard, and privacy gates, and do not touch other real repositories or push to main.
