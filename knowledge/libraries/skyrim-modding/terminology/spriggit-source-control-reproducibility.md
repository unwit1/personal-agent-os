# Skyrim Modding Terminology — Spriggit, Git, Source Control, and Reproducible Builds

Imported: 2026-09-24
Status: sourced deep-ingestion pass 10

## Source control challenge

### Binary plugin
ESP/ESM/ESL is a binary file poorly suited to line-based Git diffs/merges.

### Binary diff
Byte-level change output that usually does not convey record semantics meaningfully.

### Text serialization
Transforming plugin records into structured text representation that Git can diff.

### Round trip
Serialize plugin to text and reconstruct equivalent plugin from serialized source.

### Reproducible plugin
Binary plugin that can be regenerated from versioned text/source/tool versions with expected semantic identity.

## Spriggit

### Spriggit
Mutagen-based tool converting Bethesda plugins into Git-friendly YAML or JSON folder trees and reconstructing plugins from those trees.

### Spriggit UI
Windows graphical interface associating plugin files with serialized repositories.

### Spriggit CLI
Command-line interface supporting serialization/deserialization and Linux/automation workflows.

### serialize
Convert binary plugin to text representation.

### deserialize
Convert Spriggit text representation back to binary Bethesda plugin.

### Spriggit.Yaml
Translation package family serializing plugin records to YAML.

### Spriggit.Json
Translation package family serializing plugin records to JSON.

### Translation package
Versioned NuGet package containing actual serialization schema/logic separate from Spriggit UI/CLI.

### Translation package version
Version stamped into serialized output so older data can be deserialized with the schema that originally produced it.

### Schema evolution
Record field naming/structure changes across Spriggit/Mutagen versions.

### Automatic old-schema retrieval
On deserialize, Spriggit can retrieve the translation package/version recorded in source data, preserving old serialized definitions.

### Re-serialization upgrade
Deserialize old representation then serialize using new package version to migrate text representation to newer schema.

### Record-per-file
Spriggit folder strategy storing logical records in separate files for meaningful diffs.

### RecordData
Top-level serialized metadata/header file.

### Structured merge
Git merge over record-oriented YAML/JSON rather than raw ESP bytes.

## Git workflow

### Commit
Snapshot of source changes.

### Branch
Independent development line used for features/experiments.

### Tag
Named immutable-ish marker for release/reference state.

### Pull request
Review/merge workflow for contributed changes.

### Merge conflict
Overlapping source edits requiring resolution.

### Semantic merge conflict
Two contributors changed related game semantics even if text merge technically succeeds.

### Git LFS
Large-file storage extension appropriate for big binary assets, but not a replacement for text-serializing plugin records.

### .gitattributes
Rules defining text/binary treatment, line endings, diff filters and LFS behavior.

### Line-ending normalization
Controlling LF/CRLF so source diffs don't become noisy.

### Binary asset
NIF/DDS/HKX/FUZ/BSA/etc. that generally remains binary in Git/LFS/artifact storage.

## Reproducible mod builds

### Source tree
Version-controlled authoring inputs.

### Generated artifact
ESP/PEX/DLL/BSA/FOMOD/output generated by tools/builds rather than edited as canonical source.

### Build script
Automated procedure compiling/assembling release artifacts.

### Build manifest
Tool/runtime/dependency versions required to reproduce release.

### Dependency lock
Pinned CMake/vcpkg/npm/NuGet/submodule versions.

### Build provenance
Commit/tag, compiler/tool versions, source hashes and generated-file hashes.

### CI
Continuous integration service running tests/build/package automation on commits.

### CI artifact
Build output produced by automated workflow for testing/release.

### Release workflow
Automated process generating archive, checksums, changelog and upload assets.

### Deterministic build
Same source/toolchain produces byte-identical output. Many mod pipelines are only semantically reproducible rather than byte-deterministic because tool metadata/timestamps can differ.

### Semantic reproducibility
Regenerated plugin has same record semantics even if raw bytes/order/compression metadata differ.

### Golden artifact
Known-good output used for regression comparison.

### Regression diff
Comparison of newly generated plugin/text source against expected baseline.

## Multi-file source model

A Skyrim project can treat:
- Spriggit text as plugin source;
- PSC as Papyrus source;
- C++ as SKSE source;
- TS/JS as Skyrim Platform source;
- NIF/PSD/Blender files as art source;
- JSON/INI/YAML as runtime config;
- generated ESP/PEX/DLL/BSA/HKX/LOD as build output.

Agent OS should preserve this distinction so generated binaries do not become the only canonical source.

## Collaboration rules

1. Never edit generated binary and serialized text independently without choosing which is canonical.
2. Before merging two plugin branches, inspect semantic record conflicts after text merge.
3. Pin Spriggit translation package versions in reproducible pipelines.
4. Re-serialize after CK/xEdit edits before committing.
5. Validate deserialized plugin with xEdit/check-for-errors and regression tests.
6. Keep large source assets in LFS/artifact storage when ordinary Git is unsuitable.
7. Tag releases and record archive hashes.
8. Keep generated patch/LOD/behavior outputs reproducible but separate from hand-authored source when practical.
