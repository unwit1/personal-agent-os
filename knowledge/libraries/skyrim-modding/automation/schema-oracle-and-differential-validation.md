# Skyrim Mod Factory — Schema Oracles and Differential Validation

Created: 2026-09-24
Status: canonical strategy for double-checking generated plugin/data structures

## Objective

No single library should be trusted as the sole proof that generated Skyrim data is correct.

Use **independent oracles** where practical and compare their interpretation of the same artifact.

## Oracle hierarchy

### Oracle A — xEdit current definitions
Use as the primary plugin binary/schema oracle.

Evidence:
- xEdit's Check for Errors explicitly compares module data against its record definitions.
- unresolved references are treated as serious authoring errors.
- xDump can export xEdit's resolved definition model.

Use for:
- record/subrecord structure;
- flags;
- FormID target types;
- unresolved references;
- version-specific Skyrim schema.

### Oracle B — Mutagen Skyrim
Use as a typed independent reader/writer and load-order/link resolver.

Mutagen exposes:
- compile-time record interfaces/classes;
- binary overlay reads;
- plugin creation/writing;
- FormKey linking;
- load-order and LinkCache environments.

Use for:
- typed generation;
- independent reopen;
- FormKey/reference resolution;
- winner/context comparison.

### Oracle C — Creation Kit
Use for editor-owned semantics and official authoring behavior.

Particularly important for:
- quests/scenes/dialogue;
- navmesh;
- FaceGen;
- packages;
- world/cell spatial authoring.

CK acceptance alone is not enough; post-check with xEdit.

### Oracle D — game runtime / CommonLib
Use to prove runtime behavior that binary schemas cannot establish.

Examples:
- final actor state;
- runtime patching;
- ExtraData;
- event order;
- renderer behavior;
- animation state;
- native layout.

### Oracle E — official master data
Use local authorized Skyrim master files to establish shipped examples/defaults.

Do not commit wholesale decoded master content.

## Differential plugin round trip

For a generated plugin:

1. generate with primary backend;
2. hash artifact;
3. open with Mutagen binary overlay;
4. resolve all FormLinks against target load order;
5. run xEdit Check for Errors;
6. optionally xDump selected records;
7. serialize a normalized semantic representation from both xEdit and Mutagen;
8. compare expected fields;
9. if writer is Mutagen, optionally write a second round-trip copy and compare normalized semantics;
10. launch CK only when editor semantics are relevant;
11. game-test final behavior.

Binary byte equality is not required because order/compression/serialization details can differ while semantics remain identical.

## Normalized semantic diff

Represent a record as:
- signature;
- FormKey;
- EditorID;
- flags with schema context;
- field path;
- scalar/list/FormKey value;
- source mod;
- winning override;
- deleted/initially-disabled/persistent state;
- VMAD script/property summary;
- asset paths.

Ignore serialization-only details unless they are known to affect runtime.

## Cross-schema alarm classes

### X001 — xEdit accepts, Mutagen cannot parse
Possible:
- Mutagen definition lag;
- unusual/new record version;
- malformed edge case;
- wrong game release selection.

Do not auto-rewrite. Pin tool versions and investigate schema difference.

### X002 — Mutagen writes, xEdit reports definition error
Block release.

Treat xEdit error as likely structural defect until proven to be an xEdit-definition bug.

### X003 — both parse, semantic values differ
High priority. Determine:
- signed/unsigned conversion;
- enum mapping;
- condition encoding;
- null FormKey behavior;
- version-dependent field layout;
- localization/string representation.

### X004 — both parse, game behavior differs
The missing layer is runtime semantics:
- save state;
- runtime patcher;
- engine special merge behavior;
- ExtraData;
- native hook;
- alias/persistence;
- generated asset.

### X005 — CK changes plugin after open/save
Record the CK diff. Some data is normalized/generated by CK.

Never silently accept broad CK churn. Determine which changes are editor-owned and whether they are required.

## FormLink double-checking

Every FormLink should be validated against:
- declared masters;
- load-order LinkCache;
- expected record type;
- expected plugin identity;
- compaction/remap state.

For generated patches, reject references to mods that load after the output unless the output/master strategy intentionally supports it.

## CTDA validation

For every condition:
- function index/name;
- parameter types;
- parameter values;
- comparison operator;
- flags;
- comparison Global vs literal;
- Run On;
- Reference;
- order/OR grouping.

Use `ctda-condition-encoding-xedit.md` and `condition-function-catalog-xedit.md`.

## Record flags validation

Decode flags using parent record/base-type context, never a global bit legend.

Use `record-header-reference-flags-xedit.md`.

## VMAD validation

Check:
- ScriptName exists;
- parent/source declaration available;
- property types;
- Form properties resolve;
- fragment script names/indices;
- alias scripts map to existing alias IDs;
- generated PEX matches source/build.

## ESL validation

Cross-check:
- header flag;
- local FormID range;
- new-form count;
- references after compaction;
- external configs using FormID~Plugin;
- save/persistence migration.

## NIF differential validation

For scripted NIF transformations:
1. open source with PyNifly;
2. record block/shape/material/skin summary;
3. transform;
4. write;
5. reopen generated NIF;
6. compare invariant fields;
7. optionally inspect in NifSkope;
8. test in game.

Invariants can include:
- root name/type;
- shape count;
- vertex count when topology should not change;
- bone set;
- partitions;
- shader type;
- texture paths;
- collision presence;
- bounds.

## Papyrus differential validation

At higher-risk release stages:
- compile with Caprica;
- compile with official compiler;
- compare success/failure and source diagnostics;
- inspect PEX metadata;
- run runtime registration/API smoke test.

Compiler disagreement becomes a blocking compatibility investigation.

## Config grammar validation

For runtime frameworks:
- generate config from a typed internal model;
- parse with framework's own parser if available;
- compare resolved target count to expected fixture;
- capture unknown/ignored lines as failures in CI even if framework merely warns.

## Release rule

A schema-affecting artifact is release-ready only when:
- primary generator accepts it;
- at least one independent parser/oracle accepts it;
- all links resolve;
- xEdit structural checks pass for plugins;
- applicable runtime behavior tests pass.
