# Prior-art sweep 2026-10-17: code-context batch

Method: each repo cloned shallow into `.oss-cache/`, README and the code behind the headline claim read, nothing installed or run. Reddit is unreachable here, and web search found no r/OpenSourceAI thread for any of the five, so none is claimed as posted there. Independent evidence beyond the repos' own docs was thin (aggregator listings and vendor-adjacent reviews only).

Shared context: Agent OS already has `orchestrator/repomap.py` (planner repo map, measured to halve planner tokens) and a registry entry PA-aider (BORROW, low confidence: take PageRank ranking only if planner context quality becomes a bottleneck). Nothing here contradicts that entry. Our measured costs say tool results are about 20% of input cost, 94% of result bytes are already narrowed by grep/head/sed, and 43% of hr-cc-run4 cost was frontier retries. A code-navigation tool therefore only pays if it cuts exploration calls or retry loops, not by squeezing results. All five projects act on the worker's tool surface (MCP, hooks, instruction files) rather than on anything Agent OS owns, so the only cheap integration path is configuring the worker CLI.

## Graphify

- Repository: https://github.com/Graphify-Labs/graphify (earlier path safishamsi/graphify per ossinsight); shallow clone at 86c57be, 2026-10-16. PyPI package is `graphifyy` (double y).
- License: Apache-2.0 (LICENSE) plus a LICENSE-MIT file; third-party pages disagree (MIT vs Apache), so confirm which applies before any reuse.
- What it does: builds a knowledge graph of a codebase with local tree-sitter (no LLM for code; an LLM pass only for docs, PDFs and media), writes `graph.json`, `GRAPH_REPORT.md`, `graph.html`, and installs platform instructions/skills/hooks and an MCP server for many agent CLIs. It has grown well past code maps: cross-repo calls, SCIP and Postgres ingest, conversational memory.
- Claims vs evidence: README headline is "80% fewer tokens" and a secondary review cites "71x fewer tokens" (second hand, unverified). The only harness in the repo (`BENCHMARKS.md`, dated 2026-07-05, author-run) reports, for code, key-fact coverage 82.0% vs 70.8% for a grep/read baseline on 6 questions about ERPNext, a fixed Opus agent capped at 14 turns. That is a quality delta on n=6, not a token delta. The large memory-benchmark claims (LOCOMO, LongMemEval) concern conversational memory, a different job, with its own harness and Kimi K2.6 as judge and answerer. No independent replication found.
- Fit for Agent OS: low for code context. Heavy surface (hundreds of modules), overlaps repomap.py plus our memory work, and writes `graphify-out/` into the target repo, which collides with worktree cleanliness. The concrete idea worth noting is the always-on instruction file plus graph report as a pre-read, which we can already do with a generated map.
- Test to run: none specific to this repo. If tested at all, fold into the shared experiment below (graph-assisted vs plain grep workers). Skip unless that experiment shows a lift.
- Verdict: DEFER because its code-context benefit is measured only on 6 author-chosen questions and it duplicates our repomap while adding a large dependency and repo-writing side effects.

## repo-map

- Repository: https://github.com/noambinabout-boop/repo-map; shallow clone at 46215ac, 2026-08-19.
- License: MIT.
- What it does: single-process MCP server (about 1,200 lines of graph building in `build_graph.py`, ranking in `pagerank.py`/`rank.py`) for Python, JS/TS. Parses symbols and a call/reference graph with tree-sitter, ranks with PageRank weighted by 1/fan-in, and exposes `where_is`, `grep_code`, `outline`, `get_symbol`, `who_references`, `what_it_uses`, `refresh`. Cache lives in `~/.repo-map/cache`, nothing written into the target repo.
- Claims vs evidence: README says on "a real exploration workflow over an unfamiliar Python repo" total token cost -33% (up to -52% cold), context -64%, outline -96% vs a full read. No harness, task list, model or baseline is in the repo; `tests/` only freezes graph edges. One workflow, one author, so the -33% is an anecdote. The outline-vs-full-file figure is arithmetic about file size, not task cost. Its honest-limitations section (PageRank weaker on React, name-based edges can be spurious) is credible.
- Fit for Agent OS: the idea worth borrowing is `grep_code` returning hits situated in their enclosing symbol, and `get_symbol` reading one body instead of a file. Our workers already narrow with grep/sed, so the headroom is the same 20% tool-result slice. Python/JS only, which fits our own repo (Python).
- Test to run: offline replay on recorded worker transcripts: for each Read of a whole file followed by an edit of one symbol, compute bytes of the enclosing symbol vs the file read (stdlib `ast` is enough for Python). If whole-file Reads of files larger than the edited symbol account for over 10% of tool-result bytes, a symbol-read instruction is worth a live A/B on 10 tasks; otherwise kill.
- Verdict: DEFER because the savings figure comes from one unpublished workflow and our own measurement shows result bytes are already narrow, so test the replay before building anything.

## RepoMapper

- Repository: https://github.com/pdavis68/RepoMapper; shallow clone at 3ef8914, 2025-12-08 (no commits since).
- License: MIT.
- What it does: CLI (`repomap.py`) and MCP server (`repomap_server.py`) re-implementing Aider's repo map: tree-sitter tags via `.scm` queries, a networkx PageRank with personalization toward chat files, then a binary search on token budget to fit the map. About 1,200 lines total.
- Claims vs evidence: makes no performance claim. The README says plainly it is written from a specification of Aider's code, fed to an LLM, and shares no code with Aider. No benchmark and no tests. Last commit is 10 months old, so it is effectively unmaintained.
- Fit for Agent OS: it is a readable reference for exactly the PA-aider BORROW idea (personalized PageRank plus budget fitting) and confirms the technique is about 100 lines on top of tree-sitter tags and networkx. We would not take it as a dependency (networkx and tree-sitter-languages are non-stdlib, our orchestrator is stdlib-first). A Python-only version using `ast` fits `orchestrator/repomap.py`.
- Test to run: offline: on the last 20 planner prompts, compare files in the current repomap vs a personalized-PageRank map (import graph via `ast`, personalized on files named in the goal) against the files the finished diff actually touched; measure recall at equal token budget. Justify implementing only if recall improves by at least 10 points; the PA-aider revisit trigger (planner misses causing repeated FAILs) should also be met first.
- Verdict: REJECT as a dependency because it is stale, untested and non-stdlib, but keep the PageRank idea tracked under PA-aider.

## agentless-mcp

- Repository: https://github.com/dmarlow-personal/agentless-mcp (found via the Glama listing; GitHub search did not surface it directly); shallow clone at 9bb51ac, 2026-10-10.
- License: MIT.
- What it does: model-free tree-sitter navigation (`map`, `tree`, `skeleton`, `expand`, `slice`, `find-symbol`, `refs`, `explain`, `history`, import cycles, communities, health), plus a CLI-only write side: SEARCH/REPLACE patch parse, syntax check, worktree-isolated apply, `lint` (complexity delta, contract drift, clone delta), `validate` with a test command, and an equivalence-clustered `vote` over candidate patches. The MCP server is read-only; the patch side is not exposed over MCP. Ships hook scripts that order tool use (a gate that defers broad grep/find until a symbol-map call has happened).
- Claims vs evidence: the strongest evidence in this batch. The README cites SWE-Explore-Bench, n=60 issue-localization tasks with Sonnet, where an arm limited to agentless tools plus Read beat free choice on six localization metrics with 95% CIs excluding 0, and publishes a methodology doc and a noise-floor replicate. Caveats: the author ran it, the metric is localization (finding files/lines), not task success or cost, the winning arm removed native search tools whereas the shipped gate only defers them (the README says so itself), and the Bash-grep half of the gate is explicitly unbenchmarked. One author, early project.
- Fit for Agent OS: two pieces map onto real surfaces. (1) The tool-order gate is a CLI hook on the worker, which Agent OS can set in worker settings without owning the loop. (2) `lint`, `validate` and `vote` mirror our deterministic validators and the retry problem: pre-screening candidate patches before the validator (syntax check, complexity and contract drift) targets the 43% of cost that was retries. Equivalence clustering of identical results is a cheap trick for any best-of-n step we add.
- Test to run: offline first: run `agentless-mcp lint --diff` against base checkouts for 30 historical worker diffs that later failed a validator, and count how many the lint flags before tests ran (and false positives on passing diffs). Justify a live trial if it catches at least 20% of failures with under 10% false positives on passes. Separately, replicate localization on 10 of our own tasks with the gate hook vs none, counting calls to first correct file.
- Verdict: WRAP because the lint/validate half is deterministic, MIT, callable as a CLI by our validators, and the only project here with a published paired benchmark, though its localization gain still has to be shown on our tasks.

## code-review-graph

- Repository: https://github.com/tirth8205/code-review-graph; shallow clone at d72e8fb, 2026-10-15. A fork `better-code-review-graph` exists on PyPI; the original is evaluated here.
- License: MIT.
- What it does: tree-sitter parse into a SQLite graph (nodes: functions, classes, imports; edges: calls, inheritance, tests), SHA-256 incremental updates driven by git diff, blast-radius and risk-scored change analysis (`detect_changes`, `get_impact_radius`, `get_review_context`), communities, flows, optional embeddings, a GitHub Action, and installers for 16 agent platforms. 30 MCP tools; its own CLAUDE.md asks agents for at most 5 calls and 800 tokens per task.
- Claims vs evidence: headline is 65x fewer tokens (the README diagram uses flask: 143,594 vs 2,196). `docs/REPRODUCING.md` gives commands and a table over 6 repos (36x to 376x, and it notes the README ratio is computed differently from the benchmark's own average). The baseline is "feed the entire corpus to the model", which no real agent does; a grep-and-read agent is already far cheaper, as our 94%-narrowed measurement shows. The repo does include an `agent_baseline` benchmark and `impact_accuracy`, which are the more relevant ones, but the README leads with the corpus ratio. Author-run, unreplicated; the repo also carries 30 tools and 100+ test modules, a large maintenance surface, and an install step that rewrites hooks and instruction files.
- Fit for Agent OS: the relevant idea is the review use case. Our independent reviewers check diffs, and a changed-symbol-to-callers-and-tests list (blast radius) is the context a reviewer currently has to grep for. A stdlib approximation (git diff names, `ast` for defs, grep for callers and tests) could feed reviewer prompts without taking the SQLite graph.
- Test to run: offline: on 20 past reviewed diffs, build the caller-and-test set with a simple `ast`/grep blast-radius script, and check whether review findings recorded as valid referenced files in that set but outside the diff. If at least a quarter of valid findings sit in the blast radius but not the diff, add it to the reviewer prompt; if not, drop it. Optionally run `code-review-graph detect-changes` in a throwaway copy for comparison.
- Verdict: BORROW the blast-radius idea for reviewer context, because the review framing fits our independent reviewers and the headline ratio is against a baseline no agent uses, so take the concept and not the graph store.
