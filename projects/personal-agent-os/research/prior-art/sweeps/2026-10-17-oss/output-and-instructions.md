## Caveman

- Repository: https://github.com/JuliusBrussee/caveman, evaluated at d262ab3 (2026-10-13), shallow clone.
- License: Apache-2.0 for the whole repo per README and LICENSING.md (from 3.0.0; older releases differ). Hosted "Caveman Cloud" is separate commercial software. Name and logo are trademarks.
- What it does: started as a Claude Code skill and hook set (SessionStart and per-prompt hooks inject a terse-style ruleset; `/caveman`, `/ultracave`, modes). It now also ships a local compression engine and a provider proxy (`proxy/`, `engine/`, `shrink/`), `/caveman-compress` for memory files such as CLAUDE.md, a model/effort router ("Auto"), a code-mode "Blocks" feature, and installers for 30+ agents. Only the output-style rules and `/caveman-compress` are relevant to our surface.
- Claims vs evidence: the headline numbers are now mixed. The old "65-75% fewer output tokens" is no longer published; `docs/HONEST-NUMBERS.md` says no aggregate reduction vs default replies is committed. Its own three-arm eval (n=10, one run, output length only, tiktoken approximation) shows 3% (`/caveman`) and 35% (`/ultracave`) fewer output tokens than a plain "Answer concisely." control, while the rules cost about 1,160 input tokens. The README's "33.2% fewer input tokens" is for the proxy/engine on six synthetic file types with one buried record (HTML got 9.9% worse; README says the session run used an older engine); "54% cheaper" for Auto is an interim, half-done run on 85 tasks, mostly from lowering effort. Outside A/Bs it cites are more telling: LemonCrow, 300 runs/arm: billed output -44.1% but total cost +0.06% (skill adds ~1,500 cached tokens); a user measuring 662 Claude Code sessions found output was 0.3% of tokens and net bill effect within +/-0.2%; JetBrains 86 tasks: 8.5% fewer output tokens, no quality loss. A Cursor user reported a net loss (#550). Web search also found a ComputingForGeeks single-task comparison at about -37% total tokens; that is one task and I did not open it. This matches our measured profile: input and cache re-reads dominate cost, output prose is small.
- Fit for Agent OS: the output-style skill could be installed in worker CLIs, but our workers mostly write code and diffs, where the voice does nothing, and a worker's final report is read by the orchestrator, where terse output could cost fidelity (negations, numbers). Tool-output compression via `shrink`/proxy hits the same wall `PA-distill` documented: 94% of our result bytes are already narrowed commands. Worth borrowing is the evaluation discipline: three arms (none / "be concise" / skill) so the honest delta is skill vs terse control, and a "mode must be asserted active" check. `/caveman-compress` on CLAUDE.md-style adapter files is the only piece with a plausible input-side win (22.8-49.1% per file on its five fixtures), but those files are cached at 0.1x on re-read and our generated adapters are already short.
- Test to run: offline, no API cost. Take the real worker final-report messages from past runs (the `result` summary blocks and the reviewer inputs) and measure how many tokens they are as a share of per-run billed output and total cost from the cost ledger. If output is under about 5% of cost (the outside sessions suggest 0.3-3%), kill the idea. Only if it is larger, run `evals/measure.py` style 3-arm A/B on 10 stored planner/worker prompts with a validator-pass check.
- Verdict: REJECT, as a dependency or default instruction: measured by others and consistent with our ledger, output prose is too small a share of cost to justify 1,160 extra input tokens and fidelity risk; keep the three-arm eval method as a borrowed practice.

## token-savior

- Repository: https://github.com/Mibayy/token-savior (PyPI `token-savior-recall`), evaluated at 770e055 (2026-10-15), shallow clone. The task text named a "-43%" independent single-task benchmark; I could not find it (searches for token-savior with 43%, independent benchmark; only the README's own figures and a "-44% manifest" tool-schema figure turned up).
- License: MIT.
- What it does: a Python MCP server that indexes a codebase (per-language annotators, symbol graph, SQLite memory) and exposes about 15-18 tools such as `find_symbol`, `get_function_source`, `search_codebase`, `replace_symbol_source`, so an agent reads symbols instead of files. It also has persistent memory, bash-rewriter, hooks and a small-profile manifest (`tiny_plus`, `auto`, `optimized`).
- Claims vs evidence: the headline "97.9% at -80% active tokens" (96 tasks, Opus 4.7) comes from a harness the README itself says is not public, so "reported, not independently verifiable"; the CLAUDE.md links a separate `tsbench` repo that I did not clone. The author withdrew an August re-measurement because only 1 of 143 sessions actually called the server (tools were hidden behind deferred tool search), a good lesson. The October re-measurement (8 tasks on one frozen repo, Haiku 4.5, 3 passes, tools verified called in 23/24 sessions) shows cost -45% (range -39% to -53%), new tokens -59%, but wall time +40%; editing tasks showed no measurable gain. All of it is author-run, small, and on a cheap model; "new tokens" excludes cache reads, which dominate real cost.
- Fit for Agent OS: it acts on the agent's read/search tools, so it would be an MCP server configured in the worker's CLI, not code in the orchestrator. Our measured tool results are mostly already narrowed by grep/head/sed, so the headroom is in exploration reads, which the author says shrink only when the model actually picks the tools. Replacing native Read/Edit adds a stale-index failure mode. The useful, cheap idea is a symbol-level read tool for large files, plus the benchmark rule "assert the tool was called".
- Test to run: offline replay on our transcripts: from the 528 recorded Claude Code tool results, classify reads of whole source files (Read, cat) and estimate the bytes a symbol read would have returned using Python's `ast`. If whole-file reads are under about 10% of tool-result bytes, stop. Otherwise run 3 frozen repo tasks, with and without the server (via a worker `--mcp-config`), asserting tool calls, comparing billed cost including cache reads and the validator pass rate.
- Verdict: DEFER: plausible mechanism but every number is author-run, the main harness is not public, and our own data says reads are already narrow; revisit after the offline replay shows whole-file reads are a material share.

## claude-code-memory-setup

- Repository: https://github.com/lucasrosati/claude-code-memory-setup, evaluated at 62d0d09 (2026-10-07), shallow clone. It wraps Graphify (https://github.com/safishamsi/graphify), which I did not clone.
- License: MIT.
- What it does: a setup guide plus scripts (no framework) for Claude Code: an Obsidian vault as long-term memory, Graphify to build a tree-sitter knowledge graph of the code (AST mode, no LLM tokens), a chat-history import pipeline, `/save` and `/resume` commands, and a SessionEnd hook that writes an automatic log if you forgot to save.
- Claims vs evidence: the "71.5x per session" and "499x per query" figures are now self-labelled unsupported in the README: the 71.5x is a ~20,000 vs ~280 token illustration for one retrieval, "original payloads and tokenizer were not published", and 499x has no baseline. The repo added a benchmark protocol and an offline `summarize.py` whose fixture only checks arithmetic; no new results are claimed. A third-party write-up found by search measured about 54k vs 108k tokens on one repo with Graphify (about 2x), which is far from 70x and is a single task. The author's own correction is the most credible evidence in the repo.
- Fit for Agent OS: overlaps what we already have (git-backed durable memory, handoffs, `agent-os context`, `PA-mem0`, `PA-graphiti`, `PA-letta` entries). Obsidian is a human-facing store; our memory is in git with deterministic retrieval. The `/save` and SessionEnd auto-log pattern (write a handoff even if nobody asked) is already how our handoffs work. Graphify-style code graphs belong in the same bucket as token-savior's index.
- Test to run: none worth running on the repo. If we want the one idea that might be new, check for a gap offline: list the last 20 worker sessions that ended without a handoff file and see whether a SessionEnd-style hook would have produced one. Justified only if more than about 10% ended without a handoff.
- Verdict: REJECT: its headline savings are withdrawn by its own README, and the memory/handoff/graph functions duplicate existing Agent OS and registry entries.

## CostAffective

- Repository: https://github.com/okyashgajjar/CostAffective-MCP (the README is branded CostWise and links `costwise-mcp`), evaluated at 5aaf8f6 (2026-08-02), shallow clone. Found via an author Medium post, mcp.so listings and a guessed repo URL; the Medium page could not be fetched here (proxy refused), so the 45.9% claim is known only from search snippets.
- License: MIT.
- What it does: a Go MCP server (CGO, Tree-sitter, SQLite, about 10-11 tools) that indexes the repo for symbol/reference/call-graph queries; `remember` and `recall` for small per-repo facts; `stash_context` to park large output on disk and return a short handle; and a ~275-token session instruction delivered through the MCP `instructions` field.
- Claims vs evidence: the 45.9% number is withdrawn by the repo's own `PUBLIC_RELEASE_AUDIT.md`: "No saved artifact", with the same document family inconsistently stating 42.1% and 33.6%; other removed claims include 81.7% fewer tokens, 2.2x faster, and "same output quality". Old self-benchmarks were archived because file matching was broken (0.0% keyword coverage) or measured another project (Aider). The remaining audit-backed claims are mechanical (local, no API key, budget enforcement tests). There is no end-to-end measurement of agent cost. The install path is `curl | bash` which builds from source and installs Go; I did not run it.
- Fit for Agent OS: same surface as token-savior (a worker-side MCP server). One mechanism is interesting: stash a big output and return a handle, pulling back only a query slice. That targets the long-lived tool results (median 64 calls in context), but the model must choose to call it, and 94% of our measured results were already small. Agent OS could instead apply the idea in the validator layer, which it does own (full logs saved to disk, short excerpt to the worker, already done for retry prompts).
- Test to run: offline: from the 528 results, compute the distribution of result size and the number of calls each stays in context; count results over 8 KB and their share of tool-result bytes. If results over 8 KB are under 10% of bytes, the stash idea has nothing to act on. Otherwise prototype it only in validator output using existing code.
- Verdict: REJECT: the headline saving has no artifact and was retracted by the author's audit, and the only novel idea (stash and handle) targets large outputs that our data says are rare.
