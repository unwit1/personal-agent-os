# Prior-art sweep 2026-10-17: orchestrators-a

Method: shallow clones in `.oss-cache/`, README and the code behind each claim read, web search for independent evidence. Reddit is unreachable, and no search surfaced an r/OpenSourceAI thread for any of these five projects, so none is claimed as posted there. Star counts were not verified (GitHub API calls were blocked in this run), so none are quoted. Agent OS already does the core pattern all five share (planner, worktree per worker, CLI adapters, validators, reviewers, retry/escalate), so the question for each is what is left over.

## Composio Agent Orchestrator

- Repository: https://github.com/ComposioHQ/agent-orchestrator (README badges and links now point to OrchestratorInc/agent-orchestrator, so the project appears to have moved or been rebranded as "Orchestrator.inc"; one web review also reports a transfer). Evaluated `fb6497f`, 2026-10-17.
- License: Apache-2.0 (LICENSE file and README badge).
- What it does: a Go daemon plus desktop UI. One worker is one task, one coding agent, one git worktree. A persistent "project orchestrator" agent plans and spawns or redirects workers. An SCM observer feeds CI failures, review comments and merge-conflict state to a lifecycle manager (`backend/internal/daemon/lifecycle_wiring.go`, `internal/observe/scm`), which nudges the owning agent through its terminal. A Kanban derives each card's column from session, PR, CI and review facts.
- Claims vs evidence: the README claims planning, isolated workspaces and CI/review feedback loops; the code confirms the observer-to-nudge path and merge-conflict nudges. There is no measured benefit anywhere: no benchmark of CI-fix success, only Go micro-benchmarks for file listing. The orchestrator prompt (`session_manager/prompt.go`) forbids the planner from resolving conflicts and tells it to spawn a worker instead, so "merge conflicts" means notifying the worker, not a dedicated resolver. The gate that only pastes urgent messages when an adapter reports permission dialogs as "blocked" is careful, and specific to driving interactive TUIs.
- Fit for Agent OS: low for the product (desktop and TUI driven, long-lived interactive sessions; Agent OS runs headless one-shot CLI calls). Two ideas map: (1) derive task status from observed facts (PR, CI, review) rather than from agent self-report, and (2) on a merge conflict after integration, hand the conflict to a fresh worker with the conflicted files and both diffs instead of escalating the whole task. Module: `src/agent_os/orchestrator/` integration step and retry prompt builder.
- Test to run: grep recorded runs for integration failures caused by merge conflicts versus validator failures. If conflicts are at least 5% of failed tasks, build a fixture with a deliberate conflict and measure whether a conflict-only retry worker resolves it cheaper than a full retry. If conflicts are rare, drop it.
- Verdict: DEFER because the useful parts (fact-derived status, conflict-only retry) are small and unproven for us, and the product shape does not match headless orchestration.

## Omnigent

- Repository: https://github.com/omnigent-ai/omnigent (a similarly named `mumomo011/omnigent` also appears in search and was not used). Evaluated `903eeba`, 2026-10-16.
- License: Apache-2.0 (LICENSE file and badge). README marks status as alpha.
- What it does: a server plus CLI/web/desktop "meta-harness" that runs Claude Code, Codex, Cursor, OpenCode, Hermes, Pi and YAML-defined agents in one session, with cloud sandbox backends and shared sessions. Policies (`omnigent/policies/`, builtins: cost, safety, risk_score, routing, working_dir, cel, github, orchestration) evaluate at request and tool-call phases and return allow, ask or deny. For native CLIs the tool-call phase is wired to the CLI's `PreToolUse` hook.
- Claims vs evidence: the policy enforcement claim is substantiated in code. `policies/builtins/cost.py` has concrete semantics: soft ASK thresholds that each prompt once, a hard cap that denies only while the session is on an expensive model (a downgrade gate rather than a stop), and fail-closed denial when usage exists but cost is unpriced. It admits cost is refreshed at turn boundaries so one turn can overshoot. No savings or quality figures are claimed or measured. The any-device and sandbox claims are product features, irrelevant here.
- Fit for Agent OS: the policy engine overlaps our deterministic validators and the existing Cedar/OPA entries. The borrowable idea is the cost-budget semantics: cap spend per run, and on reaching it force a cheaper tier instead of aborting, with fail-closed handling for unpriced models. Run hr-cc-run4 had 43% of cost in frontier retries, so a "downgrade instead of retry upward" budget rule is relevant. Placement: orchestrator budget and escalation logic, plus a `PreToolUse` hook in the Claude adapter if tool-level gating is ever wanted.
- Test to run: offline replay of hr-cc-run4's per-call cost ledger with a simulated cap (for example 70% of the run's actual spend) under the downgrade-gate rule versus a hard stop. Implement if the rule would have saved at least 20% of frontier retry cost without failing more tasks.
- Verdict: BORROW the cost-budget downgrade-gate semantics only; do not depend on or wrap an alpha server platform.

## fractal

- Repository: https://github.com/plasma-ai/fractal (PyPI `plasma-fractal`). Evaluated `e0cb096`, 2026-09-17.
- License: Apache-2.0 (LICENSE file and README badge).
- What it does: autonomous agent loops in a tree. Each node iterates toward a goal in its own git worktree inside tmux and may spawn child nodes for separable subtasks. Hard caps on iterations, depth, children, cost and time (`max_depth`, `max_children`, `max_cost` config keys); run metadata including cost in one SQLite database; a TUI to steer or stop. Backends: Claude Code, Codex, Grok, opencode, omp. `fractal/_node/NODE.md` and step files are the per-iteration prompts; `fractal/core/loop.py` runs them.
- Claims vs evidence: the claim is architectural ("the tree grows to fit the problem") and the caps are real config. There is no benchmark and no comparison against a fixed plan, so nothing shows recursive decomposition beats flat. The README is candid that nodes run with approval gates disabled (`bypassPermissions`, `danger-full-access`) and that worktrees isolate only the branch, not the filesystem or network.
- Fit for Agent OS: recursion runs against our measured direction (parallelism was 1.43x, so more fan-out is not the bottleneck, and children multiply the retry cost that already dominates). The borrowable piece is a single cap set including depth and children caps, relevant only if workers ever spawn subtasks. A per-node cost row in SQLite is roughly what our run ledger already does.
- Test to run: none worth building now. If planner-spawned subtasks are added, test with a fixture goal and assert that depth, children and cost caps stop the tree.
- Verdict: REJECT because recursive loops are unmeasured, add fan-out cost, and disable permissions by default; the cap-set idea is noted for a future subtask feature.

## bernstein

- Repository: https://github.com/chernistry/bernstein (README links use sipyourdrink-ltd/bernstein; PyPI `bernstein`, 3.13.0 seen). Evaluated `65a519a`, 2026-10-16.
- License: Apache-2.0 (LICENSE file).
- What it does: a Python scheduler for 50+ CLI agent adapters. Scheduling is plain Python with no LLM in the coordination loop, driven by a YAML run spec of phases, roles and dependencies. Each coding task runs in its own worktree behind merge gates, with a replay journal, a lineage record, an approval queue (`core/approval/`), a quality-gate runner, and an opt-in HMAC-chained audit log (`BERNSTEIN_AUDIT=1`). Its README calls it beta and solo-maintained; the source tree has about 2,150 Python files.
- Claims vs evidence: closest in shape to Agent OS. Some self-reporting is candid: BENCHMARKS.md says its gate-evasion suite catches only 2 of 8 evasion classes today and its leakage suite is clean on 1 of 5 surfaces. The README says the audit chain is opt-in, so a reading of "audit chain over every step" overstates it. A SWE-Bench Lite harness (solo-sonnet, solo-opus, bernstein-sonnet, bernstein-mixed) exists in `benchmarks/swe_bench/`, but its README says the modeling harnesses are not live runs and not fit for public claims; I found no published verified result. Replay determinism covers the task graph, not agent output.
- Fit for Agent OS: three borrowable items. (1) The gate-evasion benchmark idea: fixtures that are changes which once slipped past a validator, run through the validators to measure catch rate; we can build ours from past reviewer and validator misses. (2) A hash-chained append-only run ledger; a SHA-256 chain over existing run events gives tamper evidence cheaply. (3) Replaying a recorded plan to the same task graph. Placement: `src/agent_os/orchestrator/` run ledger and validator tests.
- Test to run: collect 8 to 10 past diffs where a validator or reviewer missed a defect (from run logs and handoffs), build them as fixtures and report validator catch rate; implement a permanent suite if catch rate is below 80%. Separately, a 30-line check that chains hashes over one run's event log and detects a deliberately edited line.
- Verdict: BORROW the gate-evasion fixture idea and an optional hash chain over the run ledger; do not wrap or depend on a solo-maintained beta scheduler.

## Claude Squad

- Repository: https://github.com/smtg-ai/claude-squad. Evaluated `ce1ffb4`, 2026-08-20.
- License: AGPL-3.0 (LICENSE.md). Copyleft; treat as read-only reference and do not copy code.
- What it does: a Go terminal UI managing multiple agent sessions (Claude Code, Codex, OpenCode, Amp and others), each in its own tmux session with its own git worktree and branch (`session/tmux`, `session/git/worktree*.go`). It offers diff preview, pause and resume, an auto-yes mode, and commit and push from the UI. Merge and review stay manual, per a third-party comparison.
- Claims vs evidence: it makes no performance claims; it is a human-in-the-loop multiplexer, and the code is straightforward worktree and tmux plumbing. Independent roundups list it as a common baseline tool.
- Fit for Agent OS: nothing new. Worktree-per-worker and CLI adapters already exist; the interactive tmux layer is what Agent OS deliberately lacks, and auto-yes acceptance is a hazard for a validated pipeline. AGPL makes borrowing code unwise anyway.
- Test to run: none. Optionally read `session/git/worktree_ops.go` once to compare worktree cleanup and pause/resume edge cases with our worktree lifecycle.
- Verdict: REJECT because it duplicates what we already do without validation or review layers, and its license rules out reuse.
