## RTK (Rust Token Killer)
- Repository: https://github.com/rtk-ai/rtk, shallow clone of `develop` at 7bff768 (2026-10-17).
- License: Apache-2.0 for the CLI, filters and hooks; BUSL-1.1 for `proxy/` (API-traffic daemon) and the compression `engine`. An Apache-only `rtk-oss` edition exists. BUSL bars offering it to third parties as a commercial service, so keep it as an optional local tool, never a bundled dependency.
- What it does: a single Rust binary that runs a shell command and returns a compact form of its output (git status/diff/log, ls/tree, grep, pytest, cargo/npm/go test, ruff, docker, 100+ commands, plus a TOML filter DSL). The integration surface is a Claude Code PreToolUse Bash hook (`hooks/claude/rtk-rewrite.sh`) that calls `rtk rewrite "$CMD"` and returns `updatedInput`, so `git status` silently becomes `rtk git status`. Codex, Cursor, Gemini and others get equivalent hooks or instruction files. On filter failure it runs the raw command; raw output can be saved to a "tee" file and the agent is shown a recovery hint (`src/core/tee.rs`).
- Claims vs evidence: headline is "up to 90% smaller bash output". The repo is unusually honest that this is a byte ratio on bash output (`bytes/4`, no tokenizer), not a bill reduction (`docs/guide/resources/savings-explained.md`), and the CI floor is only 20% per filter on fixtures. The vendor numbers come from the project's own command mix. Independent search results (summaries only, not full pages): JetBrains' paired SkillsBench A/B reported +7.6% cost at low reasoning effort (p=0.004) and about 0% at high effort, with unchanged quality, and noted that Claude Code's built-in Read and Grep tools bypass the Bash hook. Quesma's Terminal-Bench 2.1 study (~1,740 attempts) said it does not recommend RTK as a generic cost saver. A separate replay of a 614M-token session corpus found rtk, headroom and caveman together saved 3.7% of spend. That agrees with our own 2026-10-16 replay: our results are already narrowed, so there is little for a formatter to remove.
- Fit for Agent OS: low. Agent OS never sees tool results (they live inside Claude Code/Codex), so the only route is a hook or instruction file installed in worker CLIs; the hook is real and cheap to wire, but the traffic it can shrink is the 6% of bytes that is not already narrowed. The rewrite also risks changing what validators and retry prompts quote. One idea is worth borrowing without the binary: the tee-and-hint pattern, which keeps full failing-test output on disk and gives the model a path, and fits the existing "retry prompts quote the failing test output" work. A per-command "did the filter drop the failing line" fixture test is also a good pattern for our own validators-output summaries.
- Test to run: offline, no binary needed. Take the 528 recorded tool results from the 2026-10-16 replay, keep those from un-narrowed `git`/`pytest`/`ls`/`ruff` commands (expect a small set), and apply a stdlib re-implementation of the three or four matching RTK filters (or run the `rtk-oss` binary in a throwaway sandbox if the operator approves installing it). Report bytes saved and, for each failing-test result, whether the failing assertion line survives. Justify a hook only if un-narrowed commands are at least 25% of bytes and the filters keep 100% of failure lines; otherwise kill it.
- Verdict: DEFER because measured savings on our traffic are near zero and independent A/B tests show no net cost gain; revisit only if a replay shows large un-narrowed git/pytest output.

## Headroom
- Repository: https://github.com/headroomlabs-ai/headroom, shallow clone at 2912b7b (2026-10-16).
- License: Apache-2.0 (LICENSE and README). Some forks and mirrors with the same name appear in search; this evaluation is of the headroomlabs-ai repo only.
- What it does: a Python (with a Rust workspace) compression layer for tool outputs, logs, JSON, search results, diffs, code and chat history. It ships as a library (`compress()`), an OpenAI/Anthropic-compatible proxy (`headroom proxy`, `headroom wrap claude`), and an MCP server (`headroom_compress`, `headroom_retrieve`, `headroom_stats`). Its pipeline is CacheAligner, ContentRouter (per-type crushers such as `smart_crusher`, `log_compressor`, `diff_compressor`, `search_compressor`) and CCR. CCR ("compress-cache-retrieve") stores the original in a local store keyed by hash and gives the model a `headroom_retrieve` tool; the default store TTL is 1800 s (`headroom/cache/compression_store.py`). Optional "output shaping" appends a terseness note to the end of the system prompt and lowers thinking effort on turns that only follow a tool result.
- Claims vs evidence: README tables show 21-57% savings on four seeded scenarios built from MCP-style outputs (`benchmarks/index_proof_table.py`, reproducible offline, measured with a provider tokenizer), and 97% on SQuAD v2 and BFCL at 19-32% compression. The README itself says savings scale with repetition and that prose and already-dense output barely compress. Those are payloads such as 100 search results or large JSON arrays, not the narrowed shell commands that dominate our traffic. The accuracy suite is QA and math (GSM8K, TruthfulQA, SQuAD), not coding-agent task success, with N=100. Output-token savings are an estimate (31.7% with a CI, labelled "estimated") unless the user sets a holdout. Third-party write-ups are mostly promotional; one secondhand report (search summary, unverified) says a Copilot trial and a Hermes Agent trial saw net cost increases because compressed-away content was re-read. CCR is the right mitigation for our measured 28-47% "model later needed the removed text" rate, but it costs an extra tool call and a cache-miss-prone retrieve, and the TTL bounds how long the original stays recoverable.
- Fit for Agent OS: three separate pieces. (1) The proxy would sit between Claude Code/Codex and the API, which is a surface Agent OS does not control today; it would also rewrite history, and our measurements say mid-session rewriting loses 2-6% to cache rewrites, though Headroom claims to keep prefixes stable (CacheAligner, append-only terseness note), which is unproven here. (2) The MCP server could be offered to workers as an opt-in tool; again it only helps on large unnarrowed payloads. (3) The reversible-compression design (replace bulky content with a stub plus a retrieval handle, and keep the original on disk) is the idea worth taking, and it could apply to Agent OS's own artefacts: handoffs, validator logs and reviewer inputs it already builds in `src/agent_os/orchestrator/`, without any proxy.
- Test to run: offline replay. Run the library's `compress()` over the 528 recorded results and the validator logs from run hr-cc-run4; record bytes saved per command class, and mark each reduced result as "content later quoted or used" using the same later-use check as the 28-47% measurement. Then repeat with CCR stubs on the reduced results and count how often a retrieve would have been needed. Justify implementing a retrieval-handle scheme only if reversible reduction saves at least 10% of total tool-result bytes with a later-use loss under 5%; kill it if the later-use loss stays near the lossy baseline.
- Verdict: BORROW the reversible stub-plus-retrieve pattern for Agent OS's own large artefacts, but do not wrap or depend on the proxy because it targets payloads we do not produce and the vendor numbers are self-measured.

## tml (Tool Manifest Language / OATR)
- Repository: https://github.com/maf404/tml, shallow clone at 452a192 (last commit 2026-04-14).
- License: Apache-2.0 (LICENSE file).
- What it does: this is not a tool-call verbosity reducer or a single-file output rewriter, contrary to the assignment text. It is a compact text format for describing API tools: `api.tml` for people and a compiled `api.min` for the model, one pipe-delimited line per endpoint (`users.get|GET /users/{id}|id:s!|{id,name,email,role}|tags`). The repo also holds a compiler (`tml-to-min.js`, `cli/`), a registry, a Node "studio" UI and a paper/spec folder. The thing it shrinks is tool schemas (the input side), not tool results.
- Claims vs evidence: headline is "77% fewer tokens than OpenAPI" (174 vs 769 for three Open-Meteo weather tools, same 100% accuracy). The sample is three tools and five scenarios on one weather API, one model family (Claude `input_tokens`), the baseline is the verbose OpenAPI JSON rather than a stripped native tool definition (the same table shows OpenAI schema at 522 and "Minimal JSON" at 251, so the real gap against a trimmed schema is much smaller), and the repo's own notes list known bugs (an id-normalization bug that fails the REST Countries spike, 0/3). Search found one Reddit post about it (subreddit not visible in the mirror, so not claimed as r/OpenSourceAI) quoting different counts (1047 vs 243) and no independent benchmark. A 2026 arXiv paper on token-optimized notations (arXiv 2605.29676, abstract-level only) shows the area is real but does not validate TML.
- Fit for Agent OS: very low. Claude Code and Codex build their own tool schemas from their internal tools and MCP servers; Agent OS cannot swap in a different schema format, and the tool schemas sit in the cached prefix, where they cost 0.1x on re-read. Agent OS's own prompt and skill files are prose, not API specs. The "tool selection" idea is only relevant if Agent OS gains its own loop (`adapters/http_api.py`).
- Test to run: a ten-minute offline count, only if the operator wants closure: take the MCP tool schemas actually loaded in a worker session, measure their tokens with a provider tokenizer, then measure the same tools after a naive strip of descriptions and examples. If the schema block is under 5% of cached-prefix tokens, which is likely, stop.
- Verdict: REJECT because it addresses tool-schema size, not tool output, the evidence is three tools on one API against a verbose baseline, and the cached prefix already makes schema tokens cheap.

## Intel Adaptive Token Compressor
- Repository: https://github.com/open-edge-platform/edge-ai-libraries, `libraries/adaptive-token-compressor`, shallow clone at 1914e10 (2026-10-17).
- License: Apache-2.0 (README badge, `LICENSE` file and `pyproject.toml` in that directory). Docs say 2026.2 is the initial release.
- What it does: a Python library with two compressors behind one `create_compressor()` factory and a `CompressionManager` that aggregates metrics. `HarnessCompressor` is section-aware: it splits a system prompt at headings (an "openclaw" profile), keeps high-value sections verbatim, and sends the rest to a separate Lingua server running LLMLingua-2 (PyTorch or OpenVINO, with a patch that protects digits). `ToolCompressor` asks a predictor LLM (default Qwen3.6-35B-A3B served by vLLM) to score each tool schema 1-5 for the current conversation, drops those below `score_threshold` (code default 2.0, docs default 3.0), and falls back to forwarding the full tool list when nothing scores or the predictor fails (`tool/compressor.py`). Several `placement` modes move the selected tools to a user or system tail to protect the prefix cache. It does not touch tool results.
- Claims vs evidence: the README and docs give no savings number and no accuracy benchmark; only per-call telemetry (tokens before/after) is built in, and the tests are unit tests with mocked or local servers, not task-success evaluations. The docs do mention trade-offs between token savings and prefix-cache hits, which matches our own finding that history edits can cost more than they save. LLMLingua-2 is a lossy, token-dropping method trained on meeting transcripts (the default model is `...meetingbank`), so it is the same risk class as the crushers we measured losing needed text. Search found only Intel's docs site, no independent evaluation and no discussion thread.
- Fit for Agent OS: low, with one useful corner. Compressing the system prompt does not apply, because the harness prompt belongs to Claude Code/Codex and is cached at 0.1x. LLMLingua on Agent OS's own generated prompts (planner, reviewer, handoff) would add a GPU/Docker service and a lossy step to a stdlib-first project. The part to borrow is per-tool relevance filtering with a safe fallback to the full set, which could matter for the number of MCP tools or skills loaded into a worker (the context compiler already loads only matched skills, so overlap is high). Tool selection by an extra LLM call per turn costs more than it saves when the prefix is cached.
- Test to run: count it against what we already do. From the recorded sessions, compute the fraction of loaded tool and skill description tokens that were never invoked in the session; if the unused share of the cached prefix exceeds 20%, prototype a deterministic (non-LLM) filter in the context compiler and compare worker success on a fixed task set. Skip the LLMLingua server entirely unless a prompt-compression replay on our planner prompts shows under 2% quality loss on validator pass rate.
- Verdict: REJECT because it needs two model services, compresses prompts and schemas that Agent OS does not own or that are already cheap through the cache, and ships no savings or quality evidence.
