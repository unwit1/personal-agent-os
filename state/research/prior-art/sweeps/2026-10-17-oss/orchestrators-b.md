# Prior-art sweep 2026-10-17: batch orchestrators-b

Method: each repo cloned shallow into `.oss-cache/`, README and the code behind
the claim read, nothing installed or run. Web search found vendor and roundup
pages only; no r/OpenSourceAI thread about any of these projects was found
(Reddit is unreachable), so none is claimed. The common finding: four of the
five are interactive desktop/CLI environments for a human supervising agents.
Agent OS already has the core of that (worktree per worker, CLI adapters,
validators), so little here is new at the orchestrator level. The useful
material is small and specific.

## Superset
- Repository: https://github.com/superset-sh/superset, shallow clone at commit 491ca53f (2026-10-16)
- License: Elastic License 2.0 (source-available, not OSI open source; forbids offering it as a hosted service). Ideas only, no code reuse.
- What it does: Electron desktop app (macOS primary, Linux experimental, no Windows) that creates a git worktree plus branch per task and runs any CLI agent (Claude Code, Codex, OpenCode, Droid...) in a terminal pane, with diff viewer, PR-comment-to-agent, browser preview and a cloud/relay layer (`apps/`, `packages/host-service`, `pty-daemon`).
- Claims vs evidence: Claim is "run many agents in parallel without conflicts". Evidence is product screenshots and vendor comparison pages (superset.sh/compare/*, which are marketing). No benchmark or measurement of any speed or quality gain; isolation is plain `git worktree`. The repo's own `HOOKS_INVESTIGATION.md` is a candid useful finding: it registers lifecycle hooks (`notify.sh`) in each agent's global user config (`~/.claude/settings.json`, `~/.codex/hooks.json`) and several integrations fired outside Superset until guarded by an env var. That is a real hazard of hook-based status detection.
- Fit for Agent OS: Low. Agent OS is headless and already does worktree-per-worker. The only transferable item is the lesson above: if Agent OS ever installs CLI hooks (for example a tool-output hook), scope them to the worktree/project config or guard on an Agent OS env var, never write to global user config. Per-agent lifecycle hook for "agent finished/needs input" is a UI feature we do not need.
- Test to run: None for the product. Cheap check: grep our adapters for any write to `~/.claude` or `~/.codex` and confirm all hook installation is project-scoped or env-guarded; a unit fixture asserting that would suffice.
- Verdict: REJECT because it is a human-facing IDE under a non-open license whose only lesson (scope hooks) is a one-line hygiene rule.

## Orca
- Repository: https://github.com/stablyai/orca (found via web search; the other "orca" repos returned, e.g. darl/orca, are unrelated or copies). Shallow clone at commit fd1c6a59 (2026-10-16)
- License: MIT (Copyright Lovecast Inc.)
- What it does: Electron desktop "agent development environment" with iOS/Android companions. Fans one prompt to several agents (Codex, Claude Code, OpenCode, Pi and many more adapters under `src/main/`), each in its own worktree, with a compare-and-merge-winner flow, SSH hosts, PR/issue linking and an `orca` CLI. Ships `skills/orchestration/SKILL.md` for multi-agent coordination: threaded messages, blocking ask/reply, task DAGs, decision gates, `worker_done`/escalation waits.
- Claims vs evidence: "100x builders" is slogan, not measurement; no benchmark found. Code evidence is large (the main process has hundreds of files, much of it worktree create/removal safety, WSL and updater handling), which shows how many failure modes worktree management has, not that it improves outcomes. The orchestration skill is only a stub; the real reference is served by the binary at runtime, so I could not read the actual protocol from the repo. The "fan out to N agents and merge the winner" idea is best-of-N, whose payoff depends on a selection signal; Orca leaves that to the human.
- Fit for Agent OS: Two ideas map cleanly. (1) Worktree safety checks: removal guards (`worktree-removal-safety.ts`, `worktree-removal-home-guard.ts`, orphan gitdir proof) are a checklist for our worktree cleanup. (2) Coordinator vocabulary (worker_done / escalation / decision gate) resembles our planner-worker-reviewer states; nothing to copy. Best-of-N with validators as the selector would fit `src/agent_os/orchestrator/` but our measured data (hr-cc-run4: 43% of cost was retries, 1.43x parallelism) argues against spending more on duplicate attempts until retries are cheaper.
- Test to run: Read `worktree-removal-safety.ts` and `worktree-removal-home-guard.ts`, list the guard conditions, and compare with our worktree cleanup code; write a unit fixture for each condition we lack (for example refusing to delete a path outside the worktree root or equal to home). No model calls.
- Verdict: BORROW the worktree-removal guard checklist only; the rest is a human-facing GUI and the best-of-N flow is not justified by our cost data.

## Scion
- Repository: https://github.com/GoogleCloudPlatform/scion (found via web search; InfoQ and DevOps.com coverage confirm it is the Google project). Shallow clone at commit 18d1bb3 (2026-10-16)
- License: Apache-2.0
- What it does: Go orchestration platform ("grove" = project, "hub" = control plane, "runtime broker") that starts each agent harness (Claude Code, Codex, OpenCode, Gemini CLI, Antigravity, others under `harnesses/`) as an independent process in Docker, Podman, Apple containers or Kubernetes, with per-agent credentials, a git worktree or clone, and a messaging layer. Agents learn the `scion` CLI through skills and instructions; the README's stated philosophy is "less is more".
- Claims vs evidence: Google describes it as an experimental testbed, and press (InfoQ, DevOps.com) repeats the README. Its own anecdotes (Scion Films, Relics of Athenaeum, software porting) are demonstrations, not measurements. The repo does have `perf/bench` (apibench, wallclock.sh) but that benchmarks the platform's API and start-up, not agent quality. Real engineering is visible: `pkg/agent/failure_memo.go` (short-TTL memo so a repeated launch failure with the same cause fails fast), `pkg/util/git.go` requiring git 2.48 for `worktree add --relative-paths` so worktrees survive being mounted at a different path inside containers, an auth fail-fast test suite, and staged secrets (`pkg/stagedsecrets`, `pkg/credentials`).
- Fit for Agent OS: The container-per-worker credential isolation is the most relevant item for a future hardened mode: workers today share the host user's CLI login. Not a near-term need and Kubernetes/hub machinery is far beyond a stdlib-first Python orchestrator. Two small items are borrowable: relative-path worktrees (git >= 2.48) if workers ever run in containers, and a failure memo that stops the orchestrator from relaunching a worker whose cause (missing auth, bad skill path) is unchanged within a TTL.
- Test to run: Offline replay of orchestrator run logs: count worker launches that failed with the identical error as the previous launch within 10 minutes. If that is more than a few percent of launches, add a TTL failure memo in the launcher; otherwise drop it.
- Verdict: DEFER because container isolation is valuable only once we run untrusted or multi-tenant workers, and the one cheap idea (failure memo) needs the replay count first.

## deepagents
- Repository: https://github.com/langchain-ai/deepagents, shallow clone at commit e80fd67 (2026-10-16)
- License: MIT
- What it does: Python harness on LangGraph/LangChain (`libs/deepagents`) with a planning tool, pluggable filesystem backends, sub-agents with isolated context, skills, memory, permissions, and context-management middleware: summarization, tool-output eviction to the filesystem, argument truncation, overflow clipping, prompt-cache handling. Also a `deepagents-code` terminal agent and an evals library (`libs/evals`).
- Claims vs evidence: "Batteries included, tuned for long-horizon work" is unmeasured in the README; the evals directory (`EVAL_CATALOG.md`, `UNIFIED_SCORECARD.md`) is a harness LangChain runs itself, so any numbers are vendor-measured and I did not verify them. Concrete defaults read in `middleware/summarization.py`: compaction triggers at 85% of the context window and keeps the latest 10% (fallback 170k tokens / 6 messages), older tool-call arguments are truncated at the same trigger, and `filesystem.py` evicts any tool result over 20,000 tokens to a file, leaving a pointer. These are heuristics with no ablation in the repo. They run inside the agent loop, which Agent OS does not own. Our measurements also cut against them: mid-session history edits cost 2-6% more than they saved because they rewrite the prompt cache, and lossy reduction dropped text the model later used in 28-47% of cases. Eviction of only very large results (20k tokens) to a retrievable file is lossless in a way crushing is not, but our 528-result replay shows 94% of bytes were already narrowed, so few results would reach such a threshold.
- Fit for Agent OS: As a dependency it would replace our CLI-driven workers with a LangGraph agent: a rewrite, and PA-langgraph is already recorded. The only transferable thing is the lossless large-output offload (write over-threshold output to a file, return head plus path), usable as a CLI hook or instruction. Sub-agents with isolated context are what our workers already are.
- Test to run: Replay the 528 recorded tool results and count those over 20k tokens and their share of input-side cost. If they are under about 1% of input cost, close this. If material, prototype the offload as a hook on a recorded session and verify that later calls re-reading the file do not erase the saving.
- Verdict: DEFER because the harness duplicates what the CLIs do, and the one lossless trick (large-result offload) has no evidence of mattering on our workload until the replay count is done.

## Pi coding agent
- Repository: https://github.com/badlogic/pi-mono (Mario Zechner), shallow clone at commit 8efd314 (2026-10-16). The README and package names now point to the `earendil-works` organization (`@earendil-works/pi-coding-agent`, `github:earendil-works/pi`), so the project has apparently moved; I evaluated the checkout I could clone and did not confirm which URL is canonical.
- License: MIT
- What it does: TypeScript monorepo (`packages/ai`, `agent`, `coding-agent`, `tui`, `mcp`, `durable`, `evals`...) with a minimal terminal coding agent. It deliberately omits sub-agents and plan mode; behavior comes from extensions, skills, prompt templates and packages. Offers interactive, print/JSON, RPC and SDK modes, so it can be driven by another program.
- Claims vs evidence: The claim is minimalism and extensibility, which the code supports. Two measurable details in `packages/coding-agent/src/core/`: `compaction/compaction.ts` defaults to reserve 16,384 tokens and keep 20,000 recent tokens, and `cache-warmer.ts` re-sends a request at 90% of the prompt-cache TTL only when expected savings exceed $0.05, with an idle continuation probability of 0.15 "measured from our own usage". That is an honest, explicit cost model, but it is the author's own data, and for us idle gaps are rare: workers run unattended and continuously, so cache expiry between calls is not our cost driver. `packages/evals` exists; I did not run it.
- Fit for Agent OS: Pi could be a third CLI adapter in `adapters/` (print/JSON or RPC mode gives a clean machine interface), mainly to run cheap non-Anthropic/OpenAI models at a lower tier, which would help the escalation ladder. The cache-warmer's refresh-only-if-expected-saving-positive rule is a reasonable design reference but does not apply when calls are back to back.
- Test to run: Read `docs/rpc.md` and `docs/cli.md`, then write an adapter spike that runs Pi in JSON mode against one recorded task prompt inside a worktree and see whether the validators and token accounting can consume its event stream. Justified only if a lower-cost model tier passes the same validators at least as often as the current tier.
- Verdict: INVESTIGATE because adapter feasibility as a cheaper escalation tier is plausible but unproven, and the canonical repository location needs confirming (badlogic/pi-mono versus earendil-works/pi).
